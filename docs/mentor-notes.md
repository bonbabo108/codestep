# メンター向け説明と理解度確認

## 1分で説明する

CodeStepは初学者が短いコード問題と解説で学ぶ講座最終課題です。DBの問題を出題し、ログインした本人の正解と進捗を保存・復元します（未公開）。専用stagingで管理者限定RLS・CRUD・本人保存・同時保存・停止/復旧を実API検証し、実画面でも保存と再ログイン復元を確認しました。認証はSupabase Auth、認可はapp_metadataとRLS・列権限です。本番は書き込み停止だけを適用済みで、旧7ポリシーからの切替試験と一部の画面異常系は残っています。

## 判断のポイント

認証はSupabase Authに委ね、独自パスワード保存を作らない。管理者フラグは利用者が変更できないapp_metadataに置く。UIは案内、SQL権限は操作/列の入口、RLSは利用者ごとの認可を担当する。JWTは発行時点の情報なので解除後の旧トークンと緊急停止を考える。ローカルのモックテスト成功は実DB成功の証明ではない。

## 質問5問と模範回答

1. **管理ボタンを隠すだけで安全ですか？** いいえ。直接APIへ要求できるため、DB側の権限とRLSでも拒否します。
2. **authenticated限定なら管理者限定ですか？** いいえ。一般ログインユーザーも同じロールです。署名済みJWTの管理者フラグを確認します。
3. **管理者ポリシーを追加すれば全員許可は無視されますか？** いいえ。PermissiveはORで合成されるため、広い既存許可を外します。
4. **フラグをfalseにすれば全端末ですぐ解除されますか？** いいえ。古いJWTが残ります。通常は更新後の拒否を確認し、緊急時はDB側の書き込みを止めます。
5. **UPDATEのerrorがnullなら成功ですか？** いいえ。対象消失やRLSで0件の場合があります。返却行とID、実DBテストでは保存結果も確認します。

## 生成AIと本人確認

Codexを調査、設計照合、管理者UI/エラー処理、SQL案レビュー、モックテスト、資料整理に利用。本番変更・動作保証・本人確認をAIが代行したとは説明しない。本人が差分、SQL、未検証事項を読み、5問を自分の言葉で説明してから提出/本番反映を判断する。

## 技術の役割を説明する

- Next.js：画面URLとビルド。独自APIルートは今回不要で、Supabase ClientからData APIへ要求する。
- React：問題/回答/保存中/エラーの状態管理。利用者が変われば個人状態を破棄する。
- TypeScript：静的な型の検査。外部応答の正当性まで保証しないので返却データも検証する。
- Supabase Auth：認証とJWT。確認メール待ちはセッションなし。自作のパスワードDBは作らない。
- PostgreSQL：問題・プロフィール・進捗の永続化とFK。現状のペア一意制約不足はコードだけでは解決しない。
- RLS：auth.uidによる本人の行と、app_metadataによる管理者をDBで区別。SQLの操作/列権限も必要。
- Vercel：ビルド成果物のホスティング。NEXT_PUBLIC設定はブラウザ向けなので秘密キーを入れない。

複数タブの重複はstagingのUNIQUEと23505処理で対策・実測したが、本番の一意制約は未適用。サーバー側の正誤証明とオフラインLWWは実装していない。設計シートのOneCode構想と分ける。

## staging実測と説明上の注意（2026-10-15追加）

実Auth9件と実ブラウザで、一般利用者がapp_metadataを自己変更できないこと、フラグ変更後も旧JWTは古い値を持つこと、JWT更新後に管理フォームが消えることを確認した。認証初期化前の送信でログイン処理が始まらない現象を修正し、初期HTMLでも入力/送信を無効化した。

同時初回保存は「DBのUNIQUE(user_id, question_id)」と「23505時の本人行再確認」を組み合わせる。stagingで実際に3要求を同時実行して1件を確認した。profiles.created_at、nullableな進捗列、既存FK2件を維持し、更新・削除ともNO ACTION。Auth FK/CASCADE/DB時刻トリガーは追加していない。構造追加は重複対策のUNIQUEだけで、本番は未適用のため現本番の一意性を保証したとは言わない。

現在はJSON式やモックだけでなく、実JWTとData APIで41項目を確認した。false/文字列true/null/欠落/user_metadata自己昇格の拒否、解除前の旧JWTに残る権限も実測した。緊急停止ではSELECTを維持して全ブラウザ書込を止め、同じ安全なポリシー定義を確認して限定権限だけ復旧した。

初期状態から安全な4ポリシーを作ることと、本番の旧7件を置き換えることは別試験。後者は単一トランザクション/排他ロック/権限停止下の再現計画を用意したが、ツール期限切れで未完了。画面の一部異常系もMacロックで未完了。成功した範囲と未検証範囲を分けて説明する。

最新判断：旧7件再現は今回の開発工程では省略し、静的な対象/全文ハッシュ/既存SELECT維持の検査と既存の実DB成功を活用する。移行SQL一括実行や複合ロールバックが検証済みになったわけではないため、本番承認時にはそのリスクを説明する。DROP POLICYの警告はポリシー変更への確認でありデータ削除とは区別する。requestStateエラーの根本原因は未特定なので、同じ要求や承認を繰り返さない。

## 公開直前レビューで説明すること

- 本番のprofiles/progressは本人RLSがあっても広いテーブル権限が残る。RLS対象外のTRUNCATE等を含むため、必要な列だけのACLへ絞る案を準備した。新しい管理者テーブルやFK/CASCADEは追加しない。
- ACL最小化と進捗UNIQUE追加を別TXにする。後者が失敗しても先に成功した安全化を保持する。ロールバックは元の状態へ戻す仕組みであり、元から安全でなかった設定を自動で直すものではない。
- ローカル実ブラウザ＋APIモック9件で削除/FK/0件/通信失敗の表示まで確認した。実DB41件と合わせて説明するが、「staging実画面で全異常系を確認した」とは言わない。
- npm/pnpmの異なる解決結果を一本化し、npm lockから一時コピーへクリーンインストールして56件・型検査・ビルドを確認した。公開時の接続先と自動デプロイ設定は別途確認する。手順はrelease-readiness.md。


## 登録不要デモの説明（2026-10-19）

公開ページの「管理画面デモ（登録不要）」から、問題の追加→一覧→編集→削除取消→確定を案内する。これは本物の管理者アカウントを共用する方式ではなく、ブラウザのメモリに独立したサンプルを持つ。再読込で元に戻り、他の閲覧者やDBに影響しない。入力検証・回答判定は本物と共用し、サンプルの保存だけを別の小さな関数にした。

本物の管理機能は有効セッションのapp_metadataとDBのRLS/列権限で守る。デモのCRUD成功をその認可試験の代用にはしない。PC/390px操作と通信0件はローカルで確認した。実スマホの認証完了、メールの配信、本人が技術を説明できるかは本人確認が必要。

Authの利用者UUIDをprofiles.idへ使うが、実DBにauth.usersへのFKはない。ER図で論理的な対応と物理FKを区別し、管理者はpublicテーブルのrole列ではなくapp_metadataに保持すると説明する。
